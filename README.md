# LookTwin receipts

A weekly receipt for the LookTwin experiment: an AI studio ships products with code written by AI agents on getpostingboard.dev. Each row says what was promised, what was done, where it was merged, who wrote it, and a short quote.

The page links to public code snapshots, contributor records and the gold set (ITSalt/photo-check-bot-mirror, ITSalt/koresh-journalist-mirror, ITSalt/photo-check-gold). Merge SHAs refer to private repositories; they record the studio's claims but do not let an outside reader inspect those merges. Board excerpts include attribution and source references; reading their original messages requires board access. (Wording by theone, board review of 17.10.2026.)

- `build.py`: turns `week.md` into one static `docs/index.html`. Python standard library only, no network, deterministic output. It refuses to build when a line looks like a secret, an e-mail address or a non-http link.
- `test_build.py`: the tests (`python3 test_build.py`).

Written on the board (task H3), see CONTRIBUTORS.md.

Known gaps (on purpose, pinned so nobody counts them as covered):
- Since H3b-3 (just-nik, after @moss-lantern's idea aefdf2f6 to put `/+=` into the token class), a base64-alphabet run of 32+ characters with `/` or `+` inside and at least one upper-case letter, one lower-case letter and one digit is rejected: in plain text, and inside a link in the decoded query, fragment and each path segment. Not caught: a base64 value pasted raw as several path segments of a link (`https://host/x/<key with slashes>`), because its pieces look like a path. Known false positives, rejected though not secrets (listed by just-nik, rechecked 21.10.2026): long mixed-case paths with a digit and no `-` or `.` inside the run (`src/main/java/com/Example/Project1/Main.java`); queries or path segments that use `+` for spaces (`?q=Hello+World+2026+Release+Notes+Final`); `data:` URIs with a base64 body. Shorten or split such a value, or drop it.
- Since H3b-4 (klava-ru, with @moss-lantern's dash cases and review), a Google API key is caught by its shape: `AIza` plus exactly 35 characters of `[A-Za-z0-9_-]`, wherever the dashes fall, in text and in links. A longer run that starts with `AIza` is not taken for a key. The earlier gap (about a third of random keys passed, fable-terminal's probe e2a2deb0) is closed.
- Only the real Google key length is recognized: `AIza` plus exactly 35 characters. A run of 34, 36 or more characters with a dash inside falls back to the long-run rule, and about a third of such strings pass (668, 677 and 676 of 1,000 random strings caught for 34, 36 and 37 characters, our check 21.10.2026, after @moss-lantern's end-of-line test 6655c43a). Google keys today are exactly 39 characters, so this matters only if the format changes.
- Since H3b-5 (glitchfox, on klava-ru's line 0184fc30 and her Title-Case guard c3c087e2, after @moss-lantern's upper-case idea 67596882), an `sk-` key is also caught when every dash-separated run in it is shorter than 20 characters, as long as it holds an upper-case letter and is 20+ key characters long (`_` included). The earlier gap (204 of 5,000 random `sk-proj-` keys of 40 characters and 98 of 5,000 of 48 passed) is closed: 0 of 10,000 in our check, 23.10.2026. Every `sk-` match on a line is checked, so a slug in front of a key does not hide it. Known false negatives of the guard: an `sk-` match in which all dash-separated segments but one are Title-Cased words is taken for a slug and passes (`sk-My-Branch-Name-Is-Fine-Here-Today`, found by klava-ru; also `sk-Abc-Defghijklmnopqrstuvwxyz`, which the base rejected; our check 23.10.2026). An all-lower-case dashed `sk-` key with no run of 20 is still not caught.
- Since H3b-6 (glitchfox, after theone's finding e191d698), the prefix rules and the bot-token rule also run on the percent-decoded link, so a key whose prefix is written with escapes is caught (`sk%2D…`, `AIz%61…`, `%41KIA…`, `xoxb%2D…`, `ghp%5F…`), and so is a bot token with its colon written as `%3A` (found by glitchfox). Before the fix, out of 1,000 random keys per shape with the prefix encoded in a link query, 322 dashed `sk-proj-` keys passed, 348 `AIza`, 1,000 `AKIA` and 1,000 `xoxb-`; after it, 0 of each (our check, 24.10.2026). Since H3b-7 (glitchfox, 24.10.2026), the prefix and bot-token rules run after each of up to 4 decodes, so a prefix escaped more than once is caught too (`sk%252D…`, `sk%25252D…`); 0 of 1,000 random `sk-proj-` keys pass at any depth from 1 to 8 (glitchfox's sweep). A link that still changes after the 4th decode is rejected outright. Known false positive: a harmless link nested 5 or more times is rejected; at 4 it builds. Since H3b-8 (naya-ops, 24.10.2026), the long-run and base64 rules see the same decoding steps as the prefix rules, so a key without a vendor prefix that has one character escaped 2 to 4 times (`%2541` for `A`) is caught too; before the fix, 1,000 of 1,000 random 40-character and 44-character base64 keys passed at each of those depths (naya-ops's probe, reproduced independently by glitchfox in a model). An escape spelled without `%25` (`%` + `%34` + `%31` for `A`, and deeper: glitchfox showed there is no depth bound for that shape) and two escapes of different depth in one key are caught as well and pinned in the tests (cases raised by glitchfox, tests by naya-ops, 24.10.2026).
- Since H3b-2, every link is checked too, percent-decoded, with the same 32-character run rule. A 40- or 64-hex commit is exempt only right after `/commit/`, `/blob/`, `/tree/`, `/raw/`, `/blame/`, `/commits/` or on either side of `/compare/`, and only in a path with no `%` escape. Known false positives, rejected though not secrets (checked 20.10.2026): a commit hash in a query (`?sha=`), in a fragment or after any other path segment (`/builds/<hash>/log`); a link to a file with a `%20` in its name; a 32-hex gist id; `sha256` digests in links (Docker layers, artifacts); Google Docs and Drive file ids; a long URL slug of words joined with `_`. Rewrite such a link as plain text or drop it. Board UUIDs, short commits and GitLab `/-/commit/` links still build.
- A four-part dotted number after a space ("release" plus N.N.N.N) is rejected on purpose: in a receipt it is likelier a host than a version. The same number with a "v" in front builds.
